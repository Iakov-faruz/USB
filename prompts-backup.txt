# פרומפט 00 — כללי עבודה גלובליים (Global Working Rules)

## מטרה
לאלף את הסוכן שיעבוד לפי הכללים של המשתמש ולא ימציא דרישות, נתיבים או התנהגויות שלא במפרט. שלב זה אינו כותב קוד — הוא רק קובע את מסגרת העבודה לכל המשימות הבאות.

## קבצים צפויים
אין קבצי קוד. הסוכן צריך לאשר את הכללים ולעצור.

## קריטריון אימות
הסוכן מחזיר את ההודעה "כללי העבודה התקבלו" ועוצר בהמתנה לאישור לפני המשך למשימה הבאה.

## מה לומדים
איך להגדיר מקור אמת (Source of Truth), משמעת ביצוע, כללי אבטחה ותהליך דיווח לפני שמתחילים לכתוב קוד כלשהו.

---

```text
PROMPT 00 — Global Working Rules

You are working on the USBGuard Approval Manager project.

SOURCE OF TRUTH:
- SRS v4.4 Final Frozen (2026-10-25) is the authoritative document.
- Do not invent requirements, paths, or behaviors not in the SRS.
- If the SRS is ambiguous, stop and report the exact issue.

EXECUTION DISCIPLINE:
- Work only on the current task. Do not proceed without approval.
- Begin with read-only inspection. Modify files only when authorized.
- Never use destructive Git commands (reset --hard, clean -fd).
- Preserve unrelated user changes.

SECURITY:
- Do not modify active USBGuard policy on the development host.
- Hardware-dependent tests run only in designated lab environment.
- Never assume removing a temporary rule guarantees device blocking.
- If state becomes uncertain, stop and report instead of auto-recovering.

REPORTING:
After every task, report: files changed, tests run, actual results,
remaining gaps, and the exact next step. Stop and wait for approval.
```

**אימות:** אין קוד. הסוכן צריך להחזיר "כללי העבודה התקבלו" ולעצור.

# פרומפט לימודי לאחר כל שלב

מסביר בעברית את המימוש שבוצע בשלב האחרון, כאילו הלומד בונה מערכת אבטחה אמיתית ולא רק מעתיק קוד.

חובה לכלול:

1. **מה הבעיה** — איזו בעיה הנדסית או אבטחתית נפתרה בשלב הזה.
2. **איך הפתרון עובד** — זרימת הנתונים והפעולות לפי סדר.
3. **הקבצים** — האחריות של כל קובץ ששונה.
4. **החלטות תכנון** — מדוע נבחר הפתרון ומה היו החלופות העיקריות.
5. **סיכונים** — מה עלול להשתבש ואיך הקוד מתמודד עם זה.
6. **בדיקות** — מה כל בדיקה מוכיחה ומה היא אינה מוכיחה.
7. **דוגמה** — תרחיש קונקרטי עם קלט, פעולות ותוצאה.
8. **שאלות לבדיקה עצמית** — שלוש שאלות קצרות לוודא הבנה.

לא לכתוב את כל הקוד מחדש. להתמקד בשינויים האמיתיים שבוצעו ובשורות החשובות להבנה. אם קיימת בעיה או מגבלה — לציין אותה במפורש.

# פרומפט ביקורת לאחר כל שלב

מבצע סקירת קוד לשינוי האחרון בלבד, מול SRS v4.4 Final Frozen (`USB.md`). לא משנה קוד במהלך הביקורת.

## מה לבדוק

1. האם המימוש תואם לדרישה שלשמה נוצר.
2. האם נוספו קבצים, תלויות או שכבות שלא לצורך.
3. האם יש נתיב כשל שאינו מטופל.
4. האם קיים מצב חלקי או לא עקבי אפשרי.
5. האם ההרשאות וגבולות הרכיבים נכונים.
6. האם הבדיקות מוכיחות את הטענה שהמימוש עומד בה.
7. האם בדיקה עלולה להשפיע על USBGuard אמיתי (אסור מחוץ למעבדה).
8. האם ה-diff מכיל שינויים לא קשורים.
9. האם תיעוד והסבר הקוד תואמים למימוש.
10. האם קודי היציאה ו-Audit מטופלים כהלכה.
11. האם קיים שימוש ב-Rule ID עדכני (לא כמזהה קבוע).
12. האם יש הבחנה ברורה בין הסרת כלל לבין חסימת התקן.
13. האם השלב עומד בקריטריוני הקבלה שהוגדרו לו.

## פורמט החזרה

- ממצאים לפי חומרה (קריטי / גבוה / בינוני / נמוך).
- דרישות SRS רלוונטיות לכל ממצא (מזהה מסעיף ב-USB.md).
- קובץ ושורה לכל ממצא.
- בדיקות חסרות.
- החלטה: `ACCEPT` או `REJECT`.

אם נמצאו ממצאים — לא מתקנים אותם במסגרת הביקורת. מציגים אותם להחלטת המשתמש כיצד להמשיך.

# פרומפט 01 — בדיקת המאגר וה-SRS (Repository and SRS Audit)

## מטרה
להבין את המצב הקיים לפני כל שינוי. בשלב זה **לא משנים קוד ולא יוצרים קבצים**.

## קבצים צפויים
אין קבצי קוד חדשים. רק קריאה בלבד של הקיים.

## קריטריון אימות
`git status --short` צריך להיות ריק (או להציג רק שינויים שלך).

## מה לומדים
איך למפות פרויקט קיים לפני שמשנים משהו, ואיך לבנות טבלת מעקב (traceability) בין דרישות סף (SRS) למימוש הקיים.

---

```text
PROMPT 01 — Repository and SRS Audit

READ-ONLY TASK. Do not modify files.

1. Run `git status --short` and report existing changes.
2. List the complete directory tree of the repository.
3. Locate and read the SRS v4.4 Final Frozen document.
4. Identify all existing scripts, tests, and configuration files.
5. Build a traceability table: for each SRS requirement ID (FR-XX, SEC-XX, OPS-XX),
   report whether it is implemented, partially implemented, or missing.
6. Identify which components from the SRS project tree already exist:
   - scripts/lib/*.sh files
   - scripts/*.sh entry points
   - systemd units
   - tests/

Do not implement anything. Return the table and stop.
```

## משימות מפורטות
1. בדוק מבנה מאגר, ענף נוכחי, מצב Git והיסטוריית commits רלוונטית.
2. אתר את כל מסמכי הדרישות, התכנון, הבדיקות והפריסה.
3. בדוק אם קיים כבר קוד, גם אם חלקי.
4. זהה שפת מימוש, גרסאות כלים ובדיקות קיימות.
5. הפק מיפוי של דרישות SRS לרכיבים ולבדיקות.
6. הצג אילו דרישות ממומשות, חלקיות וחסרות.
7. אתר סתירות בין מסמכים — אל תפתור אותן בשקט.
8. רשום את כל מזהי הבדיקות ב-SRS ואת מצב המימוש שלהן.
9. ציין אילו בדיקות מחייבות USBGuard אמיתי ואילו יכולות לרוץ בבידוד.

## ערך החזרה (לא Commit)
- סיכום המצב הקיים.
- עץ תיקיות.
- טבלת דרישה / מימוש / בדיקה.
- סיכונים וחסמים.
- סדר מימוש מוצע.

## איסורים
- אין commit בשלב זה (אין שינוי קוד).
- לא לשנות קוד, לא ליצור קבצים.

# פרומפט 02 — תוכנית מימוש בלבד (Implementation Plan Only)

להפוך את ה-SRS לתוכנית עבודה מדורגת שניתן לעקוב אחריה, על בסיס ממצאי פרומפט 01 וה-SRS בלבד. שלב תכנון בלבד — לא כותבים קוד מימוש.

## קבצים צפויים
אין קבצי קוד. רק מסמך תוכנית.

הסוכן צריך להחזיר רשימה ממוספרת של משימות עם תלויות.

## מה לומדים
איך לתכנן פרויקט בצורה הדרגתית ולא "הכל בבת אחת".

---

```text
PROMPT 02 — Implementation Plan Only

PLANNING ONLY. Do not modify files.

Based on the SRS and the repository state from PROMPT 01, create a
staged implementation plan that:

1. Covers every applicable SRS requirement.
2. Prioritizes security-critical components first.
3. Orders tasks by dependency (what must exist before what).
4. Separates: foundation libraries, USBGuard adapter, TTL engine,
   user interfaces, backup/restore, deployment.
5. For each task, specify:
   - Task ID
   - Exact SRS requirement IDs

   - Acceptance criteria

Do not implement. Return the plan and stop.
```

- USBGuard adapter.
- בדיקות G-01.
- מודל TTL ומצב.
- אישורים זמניים וקבועים.
- Reaper והתאוששות.
- CLI ו-TUI.
- פעולות מרובות.

- ייבוא וייצוא.

לכל רכיב ציין:
1. אחריות.

3. תלות ברכיבים אחרים.
4. גבולות אבטחה.
5. בדיקות קבלה.
6. דרישות SRS רלוונטיות (מזהים אמיתיים מ-USB.md בלבד, לא ממציאים).

# פרומפט 30 — סקירת אבטחה (Security Review)

## מטרה
איך לבדוק קוד שכתבת מנקודת מבט של תוקף. סקירת אבטחה מלאה ללא שינויים בקוד.

## קבצים צפויים

## קריטריון אימות

## מה לומדים
איך לבדוק קוד שכתבת מנקודת מבט של תוקף.

---

```text
PROMPT 30 — Security Review

REVIEW ONLY. Do not modify files.

Review the entire implementation for security issues:

1. Input validation and injection risks.
2. File permissions and symlink attacks.
3. Race conditions and locking gaps.
4. Error handling and information leakage.
5. Command injection in subprocess calls.
6. Sensitive data in logs.
7. Authorization bypass possibilities.
8. Rule ID handling (stale IDs).
9. Assumption that rule removal equals device blocking.
10. Recovery behavior in uncertain states.

For each finding:
- Severity (critical/high/medium/low)
- File and line
- Attack scenario
- Recommended fix

Do NOT fix anything. Return findings list and stop.
```

## משימות מפורטות
בצע סקירת אבטחה של המימוש הקיים. אל תוסיף תכונות חדשות ואל תבצע refactor רחב.

## בדוק

1. הרשאות וקבצים שניתנים לכתיבה על ידי משתמש לא מורשה.
2. שימוש ב-shell וחשיפה להזרקת פקודות.
3. parsing של קלט חיצוני.
4. log injection וחשיפת סודות.
5. race conditions ונעילות.
6. כתיבה לא אטומית ואובדן נתונים.
7. כשל Audit לאחר שינוי policy.
8. TTL ו-clock trust.
9. שימוש לא תקין ב-Rule ID.
10. הסרת כלל זמני כאשר כלל קבוע חופף.
11. reconciliation אוטומטי במצב לא ודאי.
12. restore של קבצים פגומים או מגרסה אחרת.
13. הרשאות systemd ו-IPC.
14. פעולות batch חלקיות.
15. האם הודעות הצלחה תואמות לתוצאה בפועל.

## פורמט החזרה לכל ממצא

- חומרה (קריטי / גבוה / בינוני / נמוך).
- קובץ ושורה.
- תרחיש ניצול או כשל.
- השפעה.
- תיקון מינימלי מוצע.
- בדיקה שתוכיח את התיקון.

## איסורים

- אל תתקן ממצאים בשלב הסקירה. המתן לאישור לפני שינוי.
